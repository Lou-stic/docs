# Architecture XDNA du NPU AMD

Les processeurs AMD Ryzen AI intègrent un **Neural Processing Unit (NPU)** basé sur l’architecture **XDNA** (et sa version améliorée XDNA 2). Contrairement à un GPU ou un CPU, ce NPU est spécialement conçu pour accélérer les opérations courantes en intelligence artificielle (multiplications matricielles, convolutions) avec une efficacité énergétique remarquable.

## Vue d’ensemble de l’architecture XDNA

XDNA est une **architecture spatiale** : une grille de cœurs indépendants appelés **AI Engines**, reliés par un réseau de commutation configurable.

- **Grille 4×5** (4 lignes, 5 colonnes) sur la première génération (Phoenix).
- Chaque AI Engine est un processeur **VLIW** (Very Long Instruction Word) avec ses propres registres et mémoire locale.
- Pas de caches matériels : le programmeur (ou le compilateur) doit **explicitement décrire tous les déplacements de données** – c’est ce qu’on appelle la programmation **bare‑metal** (sans couche d’abstraction).

## Types de cœurs

| Type | Rôle | Capacité mémoire |
|------|------|------------------|
| **Compute core** (AI Engine) | Exécute le code de calcul (multiplications, additions vectorielles) | 64 Ko (L1) |
| **Memory core** | Stocke des données intermédiaires pour les compute cores voisins | 512 Ko (L2) |
| **Shim core** | Interface avec la mémoire principale (L3) du système (CPU/GPU) | – |

Sur la partition 4×4 utilisée dans les travaux de recherche, on dispose de 16 compute cores, ce qui permet un parallélisme massif.

## Performance théorique

Chaque AI Engine peut effectuer **128 opérations FMA (fused multiply-add) par cycle** en précision bfloat16 (entrée) avec accumulation en float32. À 1 GHz, cela donne :

- **Par cœur** : 256 GFLOP/s (bfloat16)
- **Total sur 16 cœurs** : 4 TFLOP/s (bfloat16)
- **En int8** : jusqu’à 10 TOP/s (selon AMD)

<Info>
  Ces chiffres sont théoriques. En pratique, l’atteinte du pic dépend de l’efficacité du kernel et des transferts de données.
</Info>

## Programmation bare-metal avec IRON

AMD fournit un outil open-source appelé **IRON** (MLIR-based) pour programmer le NPU à très bas niveau. Contrairement aux bibliothèques toutes faites (Ryzen AI Software), IRON permet de :

- Charger un **kernel C++** sur chaque AI Engine.
- Configurer les **DMA** (Data Movement Accelerators) pour déplacer les données entre L3, L2, L1.
- Programmer les **switch boxes** (circuits de routage) pour connecter les cœurs entre eux.
- Utiliser des **verrous matériels** (semaphores) pour synchroniser les cœurs.

### Exemple simplifié d’un kernel de multiplication matricielle

Un kernel typique (écrit en C++ avec l’API AI Engine) fonctionne ainsi :

1. Initialise une zone de mémoire locale.
2. Boucle sur les tuiles (tiles) des matrices A et B.
3. Pour chaque tuile, utilise l’instruction `VMAC` (multiplie deux matrices 4×8 et 8×4 et accumule).
4. Utilise le double‑buffering pour chevaucher calcul et transfert de données.

Extrait conceptuel (C++ / AIE API) :

- Initialisation des buffers.
- Pour chaque tuile : lancer DMA pour charger A_tile et B_tile, attendre la fin des chargements.
- Calcul : sur 4 accumulateurs indépendants, faire `acc[i][j] += vmac(bufA[i], bufB[j])`.
- Renvoyer le résultat via DMA.

*Note : le code réel utilise des intrinsics spécifiques et gère le double‑buffering.*

### Gains obtenus grâce à IRON

Dans l’étude “Unlocking the AMD NPU for ML Training” (Rösti & Franz, 2025) :

- Les opérations GEMM (multiplication de matrices) sont accélérées de **2,8× en moyenne** par rapport à une exécution sur CPU (Ryzen 9 7940HS).
- L’end‑to‑end du fine‑tuning de GPT‑2 (124M) gagne **53% en débit** sur secteur et **40% en efficacité énergétique** sur batterie.
- Ces résultats sont obtenus avec un kernel maison exploitant pleinement les 16 AI Engines.

## Gestion de la mémoire et des données

L’absence de caches oblige à **tiler** (découper) les matrices pour qu’elles tiennent dans la mémoire locale (64 Ko par compute core). La stratégie utilisée dans l’étude :

- Tuiles de taille **m×k = 64×64** pour la matrice A, **k×n = 64×32** pour B.
- Les résultats sont accumulés **en place** dans chaque core.
- Les shim cores (L3) découpent les matrices principales en blocs et les distribuent aux memory cores (L2), qui les redistribuent aux compute cores (L1).

Ce découpage permet de maximiser le parallélisme et de chevaucher calculs et transferts.

## Comparaison avec d’autres accélérateurs

| Caractéristique | AMD XDNA NPU | GPU Radeon | CPU classique |
|----------------|--------------|------------|---------------|
| Mémoire locale | 64 Ko / core | Caches L1/L2 | Caches L1/L2/L3 |
| Programmation | Bare-metal (IRON) ou librairies | ROCm, CUDA (NVIDIA) | C++ standard |
| Efficacité énergétique (GEMM) | Très élevée | Modérée | Faible |
| Flexibilité | Moyenne (kernel VLIW) | Élevée (programmable) | Maximale |
| Usage typique | Inférence, fine‑tuning léger | Tout type d’IA | Développement, contrôle |

## Limitations et contraintes

- **Pas de cache** : toute donnée doit être explicitement déplacée. Un mauvais découpage peut saturer les DMAs.
- **Instructions VLIW** : le compilateur doit ordonnancer les instructions pour éviter les hazards (pas de stalling matériel).
- **Débit limité pour les petits modèles** : la surcharge de configuration (reconfiguration des shim cores) est amortie sur les grandes matrices.
- **Précision** : le NPU travaille en bfloat16 (entrée) et float32 (accumulation). Les modèles doivent être quantifiés ou adaptés.

## XDNA 2 (deuxième génération)

Les processeurs Ryzen AI 300 series et AI Max series intègrent XDNA 2, qui apporte :

- Plus de cœurs (jusqu’à 32 compute cores sur Strix Halo).
- Support de nouvelles précisions (FP8, BF8).
- Amélioration de la bande passante mémoire.
- Meilleure intégration avec le GPU Radeon (mémoire unifiée).

## En résumé

- Le NPU XDNA est une grille de cœurs VLIW avec mémoire locale, sans caches.
- La programmation **bare-metal** via IRON permet d’atteindre des accélérations >2,8× sur les GEMM.
- Idéal pour l’inférence et le fine‑tuning local avec une excellente efficacité énergétique.
- Nécessite une compréhension fine du tiling et des mouvements de données.

Pour la plupart des utilisateurs, les optimisations automatiques d’Amuse (modèles `_amdgpu`) exploitent déjà le NPU sans avoir à écrire de code bas niveau. Les développeurs souhaitant aller plus loin peuvent utiliser IRON.
